## Scope architecture
- **Deterministic core (plain Python rules/dependency graph) + LLM at the edges.**
  Why: this is the whole competitive differentiator per the hackathon's "must do real work" rule. The eligibility/dependency resolver (SSN requires employment + ISSS letter; bank often precedes SSN; fee deadlines are fixed dates) is deterministic and independently unit-testable with zero LLM calls. LLM handles personalization, explanation, and RAG-grounded content on top.
- **No real bank/SSA/university system integrations.** The product prepares actions (drafted emails, ICS files, walkthroughs); a human executes the irreversible click.
  Why: those systems are login-walled and brittle; this is a stated engineering/product judgment to be called out explicitly in the pitch, not a missing feature.

## LLM provider: Groq (2026-08-15, superseded Featherless)
- **Featherless credits never materialized** — user's call to stop waiting and get a different free key instead of continuing to block on it.
- **Groq** (`llama-3.3-70b-versatile`, OpenAI-compatible endpoint) — free, fast signup, well-tested tool-calling. Swap was a single-file change (`app/llm.py`: `base_url` + `api_key` + `model`) exactly because the provider was kept isolated there from the start; this is now the *second* same-file provider swap (Anthropic → Featherless → Groq), which is the payoff of that original design choice.
- **Real secrets-hygiene catch**: the Groq key initially landed in `backend/.env.example`, which is NOT gitignored (only `backend/.env` is) — one `git add .` away from a live key in commit history. Moved to `.env` immediately; `.env.example` restored to a placeholder.
- **First-ever live test surfaced two real bugs, both fixed same session:**
  1. `planner.py`'s `_STEP_TOPIC` dict was never updated when the resolver graph grew from 5→7 steps (Phase 5c) — `KeyError` on the two new steps, silently caught by the graceful-degradation path added earlier, so it went undetected until a real key existed to hit it. Fixed by adding the two missing entries.
  2. **Grounding failure, not just a crash**: the ISSS email draft endpoint had no gate on step readiness — for a student who's actually BLOCKED (no job offer, no check-in), the model confidently fabricated "I have a job offer" / "my check-in is complete" to fill in a plausible-sounding email rather than reflecting reality. Fixed by gating the endpoint on the resolver's own status (409 if `REQUEST_ISSS_ELIGIBILITY_LETTER` isn't READY/DONE) — same pattern as "mark done." The fix wasn't a better prompt; it was not asking the model to write something that isn't true yet. This is exactly the kind of failure mode "deterministic core decides, LLM only explains/drafts within those bounds" is supposed to prevent, and it's worth remembering as a concrete example in the pitch.
- Also generalized frontend error surfacing (`lib/api.ts`'s `asJson`) to always extract FastAPI's `{"detail": "..."}` on failure, not just for the one endpoint that originally needed it — a real reason ("Can't draft this yet — no job offer on file") beats a bare status code everywhere, not just where it happened to matter first.
- Verified live end-to-end after both fixes: real explanations (English + Hindi, screenshotted), a truthful email draft once Priya's prerequisites were genuinely satisfied, and the blocked-persona 409 path all confirmed via direct API calls and a rendered Tracker screenshot.

## Dependency subtasks + "mark done" + recommend-next (2026-08-15, while blocked on FEATHERLESS_API_KEY)
- **Graph grew from 5 to 7 steps** after a full review pass for missing real-world preconditions, both grounded in our own corpus (not invented): `CONFIRM_US_ADDRESS` now gates `OPEN_BANK_ACCOUNT` (`bank_account_without_ssn.md` already listed proof-of-address as a requirement), and `COMPLETE_ISSS_CHECKIN` now gates `REQUEST_ISSS_ELIGIBILITY_LETTER` (`texas_am/ssn_on_campus_employment.md` already said check-in must be complete first). The other 3 original steps were reviewed and left as-is. `app/resolver.py::done_flag_for()` exposes the StepId→StudentState-flag mapping so the new endpoint below doesn't invent its own notion of "done."
- **"Mark done" is real**, not illustrative: `POST /personas/{id}/steps/{step_id}/complete`. Guarded to only accept currently-READY steps (409 otherwise) — the resolver stays the single source of truth for what's actually actionable. Mutates the in-memory persona object directly (no DB — resets on server restart, proportionate to a hackathon demo; the `_PERSONAS` dict already held the real objects, not copies, so this needed no new store).
- **`app/recommend.py`** is a new, deliberately tiny deterministic module: among READY steps, prefer the nearest deadline, else first in graph order. Zero LLM, layered strictly on top of the resolver's output (never re-decides status). `ResolvedPlan.recommended_step_id` carries it to the frontend.
- **Real bug caught and fixed while wiring this up**: `GET /plan` used to 502 (losing the *entire* response, including the now-critical deterministic recommendation) whenever explanation generation failed — which is always, right now, with no API key. Changed to degrade gracefully: return the deterministic plan with `explanation: null` per step and log the failure server-side, rather than losing statuses/reasons/recommendation that never needed the LLM in the first place. This was a latent issue since Phase 5 that the new feature's zero-key requirement exposed.
- Frontend: "Mark done" appears on Home's Next-up card, inside the "+Add a new task" panel (as a one-click suggestion, distinct from the freeform personal checklist — clicking it completes the *real* plan step, it does not create a checklist duplicate), and on every READY `StepCard` in the Tracker. Completing a step shows an immediate deterministic update (always works) and best-effort re-enriches with LLM explanation text in the background (works once the key is live) — same layering principle as the rest of this build.
- Verified live end-to-end with a real Playwright browser run (not just typecheck): mark done on Home → flash confirmation + shifted recommendation → same completed status visible on Tracker. `scripts/verify_resolver.py` now includes a walkthrough section simulating the same loop standalone.

## LLM provider + model choice (Phase 4)
- **~~Claude Haiku 4.5 via the Anthropic API~~ → Featherless AI (OpenAI-compatible), model `MiniMaxAI/MiniMax-M2.5`.** (2026-08-15, superseded same day)
  Why the switch: the original brief locked in "Anthropic API (sponsor credits)", but no Anthropic key was actually in hand yet and a hackathon sponsor (Featherless) offered free, zero-signup-friction credits (promo code `OPENATLAS26`) via an OpenAI-compatible endpoint. Given the ~16–20hr clock, "free and works right now" beat "sign up and wait." User's explicit call, not a silent downgrade.
  Model: `MiniMaxAI/MiniMax-M2.5` — Featherless's own pick for "excellent in agentic tool use," which matters directly since intake extraction depends on reliable forced tool-calling (`tool_choice`).
  Mechanics that changed: `app/llm.py` now wraps `openai.OpenAI(base_url="https://api.featherless.ai/v1")` instead of `anthropic.Anthropic()`; tool-call arguments arrive as a JSON *string* to parse (`json.loads(tool_call.function.arguments)`), not a pre-parsed dict like Anthropic's `tool_use.input`; `.env` key is `FEATHERLESS_API_KEY`, not `ANTHROPIC_API_KEY`.
  Still true regardless of provider: both LLM calls (extraction, explanation) are lightweight — structured extraction and short grounded synthesis, not deep reasoning — so a fast/cheap-tier model remains the right fit. Swappable back to Claude later by re-pointing `app/llm.py` if the hackathon track scoring cares which sponsor's model is used — flagging that risk explicitly, not silently.
